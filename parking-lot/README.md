# Notes
1. Single responsibility: we should separate concerns for different classes. 
For example, before I was thinking having the logic of `ParkingManager` inside
of `ParkingLot` class, but it is better to separate them into two classes.
2. When using `Enum`, we can use `Size.MEDIUM.value` to get the value of the enum, which is more intuitive than having a separate method to get the size.
3. We should use Encapsulation policy to modify the state of the object, for example, we should not directly modify the `vehicle_type` attribute of the `Vehicle` class, but instead use a method to set it. This is for both security and maintainability reasons.
    - It is more secure because of atomicity. If we don't use a method to set the state of an object but directly modify the property, the code might fail in the middle and leave the object in an inconsistent state. For example, if we directly modify the `vehicle_type` attribute of the `Vehicle` class, and the code fails in the middle, we might end up with a `Vehicle` object that has a `vehicle_type` that is not consistent with its license plate.
    - It is more maintainable because we can easily change the implementation of the method without affecting the rest of the codebase. For example, if we want to change the way we set the `vehicle_type` attribute of the `Vehicle` class, we can simply change the implementation of the method without affecting the rest of the codebase. If we directly modify the `vehicle_type` attribute of the `Vehicle` class, we would have to change all the places in the codebase where we directly modify the `vehicle_type` attribute, which is more error-prone and less maintainable
4. Strategy Pattern: we can use strategy pattern to allow users to choose different rate strategies for calculating the parking fare. For example, we can have a `FlatRate` strategy that charges a flat rate for parking, and a `HourlyRate` strategy that charges based on the number of hours parked. This way, we can easily add new rate strategies in the future without modifying the existing codebase.
The trick is to have a `RateStrategy` interface that defines the method for calculating the fare, and then have different classes that implement this interface for different rate strategies. In the `ParkingTicket` class, we can have a `rate_strategy` attribute that is an instance of the `RateStrategy` interface, and we can use this attribute to calculate the fare when the ticket is paid.
